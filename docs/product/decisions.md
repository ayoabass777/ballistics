2026-10-20 — **D148 — Fixture row DLQ, @monitored loads, data-quality decorators on the API (owner: "yh and include metadata decorator for monitoring and alert as well as decorator for front end"; frontend = "data decorator pattern").** (1) Fixtures get the same row-level handling as standings (D147): `fixture_row_problem` rejects rows with no `api_fixture_id`, kickoff, status or home/away team id; they are parked at `s3://<bucket>/dlq/fixtures/rows/{api_league_id}/{season}/open.json` instead of failing the league's bulk COPY; with rows parked only the good rows' own fixtures are replaced (a parked fixture keeps its last good row); `raw.raw_fixtures_status` flags the league season; `replay_dag` retries hourly (`replay_fixture_rows_dlq`), dead after 24 + alert; daily check dataset `dlq.fixture_rows`. Applies to every full load (`load_fixtures_from_s3`: bootstrap and replay). (2) `@monitored(dataset, target_table)` (`etl/src/data_detector/monitoring.py`) wraps the standings and fixture loaders: every load writes a `data_movements` row (`row_validation`: rows in / loaded / parked, reasons, DLQ key, source, duration); the first parking opens an `unprocessed_rows` quality event and sends one alert (a failed DLQ write is an error alert); a clean load resolves it; monitoring never fails a load. (3) API payloads use the decorator pattern on data (`engine/api/data_quality.py`): a `Component` builds the page and stacked `DataDecorator`s add issues to one `data_quality: {ok, issues:[{code, section, severity, since, message, detail}]}` block — `StandingsQuality` (table incomplete, stale teams), `FixtureRowsQuality` (league has parked fixtures), `Freshness` (standings > 48 h, engine run > 2 days). Used on `GET /api/match/{id}` and `/context`; a failing decorator adds nothing. Tests: 125 passing (22 new) on throwaway PostgreSQL 16. Frontend rendering of `data_quality` not built.

2026-10-20 — **D147 — Unprocessable records: S3 dead letter queue, hourly replay, incomplete-table flag (owner: "let's use the json on s3 … retry in an hour"; give up after 24 h "yh"; "same for fixture dlq").** Errors are handled by kind: network errors (DNS, timeout, 5xx, 429) retry the task with backoff and only go to the DLQ once retries run out; data errors (a bad row in a good response, e.g. a standings row with no team id — Club León, Liga MX, 15 and 17 Oct) never fail the task: the row is parked as JSON at `s3://<bucket>/dlq/standings/{api_league_id}/{season}/open.json`, the rest of the league loads with pruning off, and `raw.raw_league_standings_status` flags the league; our-side errors (auth, unexpected constraints, bugs) fail loudly and are not DLQ'd. Every DLQ entry (standings and fixtures) carries its own retry state: `replay_dag` now runs hourly and retries an entry one hour after its last attempt; after 24 failed attempts it is `dead`, alerted at once and no longer retried; a clean replay or nightly refresh moves it to `dlq/resolved/`. Rows are routed by the `@dead_letter(validate, park)` decorator (`etl/src/dlq.py`). The flag reaches dbt (`mart_league_standings.standings_incomplete`, `is_stale_row` for the team's last good row, which no longer drops out of the table and no longer hides it via `ranks_repeat`) and the match page API (`table.incomplete`, `table.unprocessed_rows`, `row.stale`, `position.stale`). The daily data check gets `dlq.standings` and `dlq.fixtures`: open < 24 h warning, dead / older / flagged-but-not-in-S3 error. Tests: `tests/test_dlq.py` (20) + detector/flow/standings/match suites, 99 passing on a throwaway PostgreSQL 16; mart SQL checked against sample rows. Frontend rendering of the flag not built.
